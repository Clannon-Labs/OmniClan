## Problem:
### Server returning internal server error

> I uploaded a 122.2MB video and I was repeatedly getting 500 error.
> I put println!() statements everywhere to see where am I doing wrong,
> I didn't have any clue even after few hours, but finally after spending some more time,
> I got my answer

## Suspects after repeated attempts
1. Trying to write manifest while the file isn't even uploaded.
	- File: backend/crates/media/src/workers/upload/handle.rs: line 70
2. Not creating  the staging path at all but trying to upload file there
	- File: backend/crates/media/src/workers/upload/paths.rs: line 19 (newly added)

---

## Session summary
> After going through print debugging session of hell, I found the actual culprit
> which was more of a logic bug that code error ( I am so shocked that even after this 
> big of a refractor in a new language (for me), I didn't make much syntax errors at all )
> without even compiling the code to see the errors.. crazy!!

### Culprits
1. Uploaded video not having audio to extract from
  > I didn't even realize that the video I uploaded doesn't have an audio at all.
  - File: backend/crates/media/src/workers/upload/states/processing/video.rs: line 68
  
  > I was throwing an error if the user uploads a video with no audio instead of gracefully
  > handling it

2. Not checking if the parent directory exists or not before attempting to create a file
  - File: backend/crates/media/src/workers/upload/utils.rs: line 22 (newly added)

  > I found out that this was also a reason, so I added a small check and directory
  > creation, and it solved a part of the problem

## Potential solution (for bigger problem)
> Return a warning message instead of throwing an error
> It feels simple but I am yet to think of a robust (or just working lmao) way to handle it.

> And maybe move the media into failed/ directory instead of throwing an error
> or just giving a warning message (see more explanation below in ##Bigger Picture)

## Bigger picture
> I have also seen that even after moving the files from staging to processing,
> files in staging/ are still there which were supposed to be deleted.

> I think instead of moving file around from directory to directory just to indicate its status,
> we should keep it in a directory, modify/add inplace and note its status in manifest.json

> And create a new failed directory to indicate the failed media which will help
> the future recovery workers.

> Like if the error occured even though the media wasn't a problem in itself, we
> can retry later and process it and throwing a last attempt error and deleting it
> if the media itself is a problem
